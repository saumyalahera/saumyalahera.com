Requirement

Deliver a simple iOS API that captures camera frames in real time and renders a shirt aligned to a person’s body. Under the hood it’s ML + graphics, but the product requirement was reliability: stable latency, cancellation, and compatibility across iPhones.

  • Stable capture + buffering from AVFoundation
  • Consistent per-frame lifecycle (IDs, timestamps, cancellation)
  • Immutable “frame state” handed to rendering

Architecture

Layered modular architecture with a real-time pipeline core. Each stage owns a single responsibility and communicates through explicit value contracts (not shared mutable state).

  • Capture → Preprocess → Inference → Postprocess → Render
  • Backpressure + drop/skip policy to protect UI
  • Instrumentation for p50/p95 latency and frame drops

Why a custom ML API

TFLite or Core ML can “run a model.” My problem was an iOS system that needed predictable latency and pipeline control. I needed a stable API surface that could manage tensor composition, sparse/dense representations, and execution policy.

  • Tensor composition: shape/stride/layout + batching
  • Sparse + dense: handle intermediate ops efficiently
  • Execution policy: cancellation, timeouts, backpressure
  • Backend swap: keep call-sites stable as internals evolve

MPS integration

Used Metal Performance Shaders to accelerate key ops and keep the pipeline GPU-friendly, improving latency and power/performance on Apple silicon.

  • Reduced CPU work → protected the main thread
  • More stable frame times on supported devices
  • Better sustained performance under thermal constraints

Device issues: heating + performance variance

After functional correctness, the hardest part was shipping behavior across iPhones. Older devices heated sooner and couldn’t sustain the same frame budget, so I built graceful degradation.

  • Capability tiers (device-aware configs)
  • Dynamic input scaling under load
  • Thermal-aware quality reduction before throttling

Drawing tools: CoreGraphics → Metal

I prototyped drawing on the shirt with CoreGraphics, but moved to Metal to support textured tools (pencil grain, paint opacity) and correct mapping onto the garment surface.

  • Why texture mapping: each tool samples a different brush texture
  • GPU compositing for consistent blending on the shirt
  • Scalable: add tools by adding textures/shaders, not CPU raster hacks

Scalability + correctness (races, stale overwrite)

Real-time pipelines fail via subtle bugs: out-of-order completion, stale results overwriting newer frames, and shared mutable buffers. I enforced correctness through IDs, cancellation, and single-writer state.

  • Frame IDs to reject stale inference outputs
  • Cancel in-flight work when newer frames arrive
  • Single-writer updates; immutable frame state to rendering

Roadmap (the journey)

This roadmap matches how I present the story in interviews: start from requirements, then prove engineering maturity.

Phase 1
Requirement + API shape: define frame contracts, lifecycle, and stage boundaries.
Phase 2
ML runtime: tensors (dense/sparse), composition, execution policy, instrumentation.
Phase 3
Acceleration: integrate MPS where it improved latency/power.
Phase 4
Cross-device shipping: capability tiers, scaling, thermal policy, fallbacks.
Phase 5
Drawing tools: CoreGraphics prototype → Metal for texture-mapped brushes.
Phase 6
Concurrency hardening: prevent stale overwrite, fix races, enforce cancellation.
Next
Extensions: occlusion, more garments, deeper telemetry, QA harness.

Data Flow

How to present this: walk top-to-bottom. Emphasize that frame-state is immutable and correctness is enforced by IDs + cancellation + single-writer updates.

What I highlight while explaining

  • Isolation: each stage owns its data; no shared mutable buffers across threads.
  • Correctness: results carry a frame ID; stale inference outputs are discarded.
  • Responsiveness: cancellation + backpressure prevent UI stalls.
  • Scalability: “Policies” are pluggable—device tiers and thermal limits don’t leak into business logic.
  • Testability: each stage can be unit tested with recorded frames and deterministic inputs.
